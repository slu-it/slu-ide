# 0049. Pushing from a non-modal Push dialog, with a lease of an explicit commit for force pushes

- Status: accepted
- Date: 2026-10-17

## Context
Thoreau can commit ([ADR 0048](0048-commit-tab.md)) and fetch ([ADR 0043](0043-git-log-fetch.md)), but not push.
IntelliJ pushes from a Push dialog (Ctrl+Shift+K): the branch, the remote and the target branch at the top, the
outgoing commits and their files below, Push with Force Push in its menu, and "Commit and Push…" in the commit tool
window. A push talks to a server like a fetch: it may wait for credentials, an ssh passphrase or a slow `pre-push`
hook. A force push may throw away commits that others pushed meanwhile. Writes run one at a time on the log's
`RefWriter` (`sluide-git-write`, ADR 0041).

## Decision
- **The user's choices (2026-10-17):**
  - **A dialog that is not modal,** owned by the IDE window, so that it stays above it while the diffs it opens can be
    looked at in the editor. Rejected: a modal dialog (IntelliJ's), which would block the editor tabs its diffs open
    in.
  - **Force push with a lease of an explicit commit:** `--force-with-lease=refs/heads/<target>:<commit>`, the commit
    the dialog showed for the target's remote-tracking ref, or empty for a branch the remote did not have ("it must not
    exist"). Never plain `--force`, and never a lease without a value: a fetch in the background between looking and
    pushing would move the remote-tracking ref and so weaken a lease that git reads from it.
  - **Protected branches:** Force Push is disabled for `main` and `master` in any case (`Main`, `MASTER`: some remotes
    treat refs case-insensitively; `PROTECTED_BRANCHES`, a constant; a setting can come later). The dialog says why
    once the user opens Push's menu.
  - **Shortcut+Shift+K** (IntelliJ's) opens it from Git → Push…; the editor's delete lines moved to Shortcut+Y for it
    (the note below the table of [ADR 0022](0022-editor-key-bindings.md)).
  - **Commit and Push** in the Commit tab (Shortcut+Alt+K, IntelliJ's) commits, and opens the dialog only once the
    commit is made; a failed or cancelled commit does not open it.
- **The command** (`GitPush.push` in `modules/git`):
  `git push --porcelain --recurse-submodules=no [--set-upstream] [--force-with-lease=refs/heads/<t>:<expected>]
  --end-of-options <remote> refs/heads/<b>:refs/heads/<t>`, run as a fetch is (ADR 0043): `GIT_TERMINAL_PROMPT=0`, ssh
  in batch mode unless the user configured an ssh command (`fetchEnvironment`), 10 minutes, then stopped, cancellable
  with a `GitCancellation`. Full refnames on both sides, so that a branch and a tag of the same name are never
  confused. Names that cannot be passed to git or start with `-` (`refusal`), and an expected value that is not a full
  hash, fail without running git.
- **What git 2.53 does** (verified in `GitPushTest` against real repositories and a bare remote):
  - `--porcelain` writes one status line per ref on standard output (`<flag> TAB <from>:<to> TAB <summary>`), the rest
    on standard error. The flag of the pushed ref says what happened: `!` rejected, `=` up to date, `*` a new branch.
  - A rejection ends with exit value 1 and a reason in parentheses: `(fetch first)` when the remote has commits git has
    not seen, `(non-fast-forward)` after a fetch, `(stale info)` when a lease fails; anything else, e.g. a declining
    `pre-receive` hook, is another rejection. A failing local `pre-push` hook is a failure without a status line.
  - An empty lease value means "must not exist": a force push of a new branch fails as stale once the branch appeared
    on the remote.
  - `--set-upstream` writes `branch.<b>.remote` and `branch.<b>.merge`; it is passed only when the branch has no
    upstream yet (`branch.<b>.merge` unset), so an upstream the user set up stays.
  - `--recurse-submodules=no`: no submodule is checked or pushed, whatever `push.recurseSubmodules` says.
- **Where a push goes by default** (`pushTarget`): the remote is the first that is set of `branch.<b>.pushRemote`,
  `remote.pushDefault`, `branch.<b>.remote` (unless `.`, a local upstream), else the only remote, else `origin`, else
  the first remote; the branch is `<b>` itself, as git's default `push.default=simple` would push it: simple refuses
  to push to an upstream of another name, and a branch created from `origin/main` tracks it (`branch.autoSetupMerge`),
  so taking the upstream's name would push `feature` into `main` without force. Only with `push.default=upstream` (or
  its old name `tracking`) is the branch the upstream's (`branch.<b>.merge`), if the remote is the upstream's.
  The dialog starts with it; the target branch can be edited (checked like a new branch's name, `nameProblem`) and,
  with several remotes, the remote chosen.
- **Remote-tracking ref** (`trackingRef`): where the first of `remote.<r>.fetch` maps `refs/heads/<t>` (a glob or an
  exact refspec), else `refs/remotes/<r>/<t>`. Whether it exists decides "New".
- **What a push sends** (`outgoing`): with the tracking ref, `git log HEAD ^<ref>`; without it (a new branch), the
  commits that no remote-tracking ref of that remote has (`--not --glob=<where its refspecs write>*`); newest first,
  at most 1000 listed ("1000+ commits" and "and more…" beyond). Also how many commits the ref has that `HEAD` has not
  (`behind`; a normal push will be rejected), the commit the ref is at (the lease's value) and the `base` to diff the
  whole push against: the merge base with the ref, for a new branch the first parent of the oldest outgoing commit
  (none for a root commit, and none when the remote has no remote-tracking refs yet: then every commit is outgoing
  and the oldest is a root). "All N commits" shows the files of `HEAD` against that base, a commit its files against its
  first parent; Show Diff opens them in an editor tab as the log does (ADR 0038).
- **No fetch first:** the dialog shows what the last fetch saw ("As of the last fetch of origin."). The lease of an
  explicit commit makes a force push safe against what was not fetched, and a normal push is rejected by the server
  when the remote moved; fetching is the header's Fetch.
- **A rejection is explained in the error dialog** "Push Failed" ("main could not be pushed to origin/main."), its
  first line saying what to do ("origin/main has commits that your branch does not have. Fetch, then merge or rebase,
  or force push."; for a failed lease "origin/main changed since your last fetch. Fetch and check it before force
  pushing."), then git's message. Rejected: IntelliJ's Merge/Rebase dialog, which would need pull, merge and rebase
  that Thoreau does not have.
- **Disabled Push, with the reason:** a detached `HEAD`, no commit yet, no remote ("Add one in a terminal: git remote
  add <name> <url>."), an invalid target name, while reading, while another operation runs, and when the target
  exists and has every commit of `HEAD`: "Everything is up to date." when it is at `HEAD` (Force Push is disabled
  too: it would move nothing), "Your branch is behind origin/main; nothing to push." when `HEAD` is behind it (Force
  Push stays, unless the branch is protected: it moves the target back; Push's own label is muted then). A new branch
  without new commits can be pushed ("No new commits: pushing creates origin/feature at 1a2b3c4d."). With the remote
  ahead and commits to send (diverged), Push stays enabled with a note, so that the user sees git's answer, as
  IntelliJ does.
- **Threads:** the dialog reads on a thread of its own, `sluide-git-push` (newest read wins; an edit of the target is
  read after a pause of 300 ms), again whenever it gains the focus or is opened again while open, and when an
  operation such as a fetch or commit ends (the user may have committed, fetched or checked out meanwhile; another
  branch takes its defaults again). Push and Force Push take what was read last, the force push's question and its
  lease the same. The push is a `RefOperation` (`PushOperation`) on
  `sluide-git-write`: the header says "Pushing main to origin/main…" (or "Force pushing …") with Cancel, then "Pushed 3
  commits to origin/main.", "Pushed main to origin/feature (new branch).", "Force pushed main to origin/main." or
  "Everything up to date."; a cancel says "Push cancelled." without a dialog; the log reads again afterwards. It
  changes no files, so no unsaved editors are asked about. As for a fetch, another folder or closing the window cancels
  a running push (git stops; the server moves a ref completely or not at all).
- **One dialog per window:** Push… again brings it to the front; another folder and closing the window close it. It
  opens also while an operation runs, with Push disabled until it ends.

## Consequences
- A branch can be pushed, to the same or another name and remote, with its upstream set the first time, and forced
  with a lease that never loses commits the user did not see.
- Not done: pushing tags, skipping hooks (`--no-verify`), pushing several branches at once, IntelliJ's "Push All up to
  Here", defining remotes (a terminal does it), pull, merge or rebase after a rejection.
- Protected branches are fixed to `main` and `master` until there is a setting.
- One more thread per window while the dialog is open.
